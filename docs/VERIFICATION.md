# 検証の契約

## 1. 六つの状態を別々に持つ

| 状態 | 必要な証拠 |
|---|---|
| SOURCE | ソース生成・差分・独立部分のテスト |
| BUILD | 採用UE版のUBT/UHTによる対象プラットフォームの成功ログ |
| ASSETS | 実Editorでインポート・生成・ロードできる資産、Binding、マップ |
| RUNTIME | 実際のゲームで移動、カメラ、保存等を実行した結果 |
| VISUAL | 実UE画面と動画、参照との差分、所有者の承認 |
| PERFORMANCE | 指定機材・設定・ルートの実測ログ |

`PASS / FAIL / NOT_RUN / BLOCKED`を使用する。ファイルがない、GPUがない、資産がない等の理由を保存する。
クラウドでPythonの構文検査が通った場合はSOURCEの部分確認だけ。UEのAutomationもEngineへの依存があるので、外部の一般テストと区別する。[S8][S9]

## 2. クラウドの検証

現在の配布物では `python3 scripts/validate_handoff.py` が文書と参照画像だけを調べる。
実装が追加されたらJSONスキーマ、純粋ロジック、アセットmanifest、変換入力の検査を追加する。UEがないタスクでUHTやShaderの成功を捏造しない。

M1では`python3 scripts/check_source.py`を追加しました。実Editorが使う`recipe_contract.py`の保護ロジックと、実Characterが使う`Logic/CameraPolicy.h`を直接テストします。結果は`validation/source_checks.json`、ログは`Artifacts/SourceChecks/`です。UEクラスの構文・ヘッダー生成・リンク、UE入力、CharacterMovement、SpringArm、材質ノードのAPI／実行はこの独立チェックの対象外です。
パイプラインの独立部分をテストする際は、小さなfixtureを使い、実アセットを破壊しない。

## 3. Macのビルドとアセット

対象UE版・Xcode版・CPUアーキテクチャを記録する。ProjectとEditor targetを区別し、ログの終了コードと根本エラーを残す。
初回のShaderコンパイルやDDC生成を通常のフレームレートに混ぜない。ただし初回起動時間そのものは別途記録してよい。
生成したアセットは存在だけでなく、ロードとマップ参照を確認。Groomでは正しい基準メッシュとBinding、ルートUV、スケールを検査。
仮モデルから本モデルに差し替えた後も、Cook時に参照資産が欠落しないか確認する。

`-NullRHI`は描画をしない検査に限定する。そこでの成功をShader・毛・影・GPU性能の検証に使用しない。
コマンド実行経路がGUI描画を必要とする場合は、実際のEditor上で確認したと記録する。

## 4. 実画面

4つの固定カメラの原寸画像を取得。ファイル名にはShot ID、コミット短縮ID、Quality名を付ける。
各画像とともにEngine版、プラットフォーム、出力・内部解像度、AA／アップスケーラー、毛方式、光、露出、カメラ・姿勢情報を保存する。

合成した前後比較を作る場合も、元画像は残す。生成AI画像による改善予想を別途作っても、実画面フォルダーへ混ぜない。
Path TracerやMovie Render Queueの時間をかけた絵は、ゲーム中のリアルタイム絵と別のフォルダー・名称にする。Groomは描画経路で見た目が異なる場合がある。[S5]

## 5. 動いている状態

待機5秒、歩行10秒、停止とカメラ旋回10秒、近遠移動5秒以上を基本に、30秒以上を確認。
LOD境界、逆光、明るい窓の前、顔のアップ、足元でちらつき・残像・浮き・めり込みを検査。
平均的な良い瞬間の静止画だけを選ばない。既知の問題は見える状態で記録する。

## 6. 性能測定

### 固定条件

機材の正確なモデルとGPU、ユニファイドメモリ、macOS、UE/Xcode、電源接続と省電力設定、他アプリ、ウィンドウの実ピクセル数、パッケージ／Editorの区別を記録。
1080p出力を基準にする。Screen PercentageとTSR等の設定を記録し、「4K出力＝4K内部描画」と扱わない。

### 手順

同じコミットとカメラルートを使う。初期コンパイルを終え、30秒ウォームアップ、120秒測定を3回。
計測時は録画を切り、VSyncやフレーム上限の扱いを固定。動的解像度を使う運用でも、比較測定では固定したランを別に用意する。
CPUフレーム、GPUフレーム、p50、p95、最大停止、使用メモリ、スワップ増分、温度／スロットリングを取得可能な範囲で報告。利用できないカウンターはnullと理由を残す。

初期目標はM3 Maxで通常設定のp95フレーム時間33.3ms以下。実プレイは別に30fps上限で安定性を確認する。未達時は条件・画質・測定結果を提示し、相談なく軽量化でごまかさない。
パス別には毛、影、Lumen、後処理を切り分ける。単純なパス時間の合計はGPUの並列処理を含むフレーム時間と一致しない場合があるため、最終的に全フレーム時間で比較する。[S6][S7]

## 7. ゲームの検証

移動のフレームレート独立性、ジャンプ・着地、外周、家具の角、カメラ衝突、ポーズ解除時のキー残留を確認。
星8個へ実到達し、同じ星の再回収が加算されないこと、クリア前後に休憩が正しく変わることを確認。
セーブは実ファイルに保存してプロセスを終了し、次の起動で復元する。インメモリの疑似Storageだけで永続化確認済みにしない。
読み取り不能セーブ、設定欠損、不正な位置からの復帰も試す。リセットと既存セーブ削除には確認が必要。
フォトモードはUIなし画像保存、ゲーム復帰、品質設定復帰を確認する。

## 8. 結果の返し方

`templates/LOCAL_REPORT.md`を使う。実行日時とコミット、再現コマンド、ログの場所、画像／動画の場所、失敗の根本エラー、次に直す一点を記入する。
`templates/benchmark_run.json`のnullを実測値で埋める。架空の値や他GPUの結果で埋めない。
大量のログや大きな動画は必要範囲に絞り、個人フォルダー名・シリアル・認証情報を除いて共有する。
